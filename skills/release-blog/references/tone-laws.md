# Tone laws（Owner 法令汇总）

SKILL.md 只留索引，完整法则在此。日期是法令生效日，冲突时取最新。

## 指标门禁的边界（全绿 ≠ 不 AI）

`scripts/ai-tone-metrics.mjs` 的两条易踩正则口径：

- `顿号罗列≥3` 数的是 `A、B、C` 三连（每段 ≤10 字），"A、B、C、D、E"
  只算 1 次；改法是把三连拆成「A、B 与 C」或换成「、」以外的分隔。
- `空转句引列表` 的 `[：:]\s*(\n[-*]…)` 里 **`\s*` 会跨行**，所以「段落
  以冒号结尾 + 中间夹一张图片 + 后面跟列表」也算一次 → 冒号改句号即可。

**全绿 ≠ 不 AI（2026-09-09 实测）**：7 篇原文在这个门禁上**全部零
告警**，但读起来仍偏 AI。原因是它只量正则能抓的表层特征，而实际的
AI 味在 craft 层，具体是三条 Owner 法令的违反 ——

1. 一篇文只讲一个版本（背景节写版本编年史、中间版本进叙事）；
2. 版面占比 ≈ 决策价值（发布管道、fixtures、CI 占了用户价值的位子）；
3. 专有名词预算 + 大白话价值句（亮点先讲机制、后讲或不讲读者所得）。

加上一类非法令但同样致命的：**自我标榜的形容词**（「诚实的限制清单」
「照实说」「不是营销数字」）—— 读者没有质疑过，辩护句只会显得心虚。
结论：门禁只用来兜底，判断一篇是否偏 AI 必须回到 craft 层逐条比对。

## 平实基调（2026-09-07，全站默认）

平实风格是默认基调，不是可选风格。参照系是 unipty v0.2.2 的
zigpty 路由文（2026-09-07-unipty-v0-2-2）：

- **宣告句直陈**：发布了什么、一句话定位，完事。不写"走了两步"
  "从 X 到 Y"这类版本旅程框架，不用标题复述叙事弧。
- **一篇文只讲一个版本**：合并发布或能力跨 tag 落地时，中间版本
  不进入叙事（不提它的发布时刻、门禁变迁、changelog 分段）；
  版本号只允许出现在 substrate 固定版本与 npm 安装命令里。
  **Owner 先例 2026-09-10（opentray v0.23.0）**：8.5 小时内连发
  0.22.0 与 0.23.0 时，Owner 选择合并成一篇 v0.23.0，把「图标内核 →
  图标管线」当作一条跨 tag 落地的能力弧来写。执行方式（可复用）：
  站在**最新版本**的立场写，所有内容都以「现在」陈述（0.23.0 的依赖
  里确实含 @opentray/icon@0.23.0，读者装最新版就能全拿到），正文不出现
  中间版本号，只在链接栏把两个 release 永链都列出来做溯源。这样既守住
  「不写版本编年史」的实质，又不丢中间版本的信息。
  **第二次先例 2026-09-13（opentray v0.27.1）**：Owner 再次要求把
  0.24.0 到 0.27.1 五个版本合并成一篇。同一套执行方式照用，只是
  「链接栏永链」那一列要按版本逐个铺开（5 个 release tag 一行）。
  五个版本合计三处能力（九语言向导、多 webview 编排、扩展事件推送），
  仍然按主题归组、均衡覆盖，不按版本分段。篇名与 frontmatter 的
  `version` 取最新那个（0.27.1），`date` 取最新那个 release 的
  `published_at`。
- **对比用表格 + 数字**：优缺点横向对照，客观陈述，别一惊一乍。
- **致谢只致谢**：对象是人与社区。复核轮次、阻塞修复数、CI 过程
  一律不进致谢；要提最多在「其余变更」一句话，通常不提。

## 句级与内容法则

- 开发者对开发者；兴奋通过能力声明与数字表达，不通过形容词。
- 数字优先于形容词（体积/耗时/依赖数/issue 数）；性能声明带基线。
- **聚合数字必须说明口径，且可复现（2026-09-11）**：写进正文的
  `N 个 feat / N 个 fix` 这类统计，一律用严格口径
  `git log A..B --pretty=%s | grep -cE '^fix(\(|!|:)'`（按 conventional
  前缀计类型）。**不要用 `grep -ci fix`**——它统计的是「主题里出现过
  fix 字样」的提交，会把 `docs: fix the …` 也算进去，把 49 报成 73。
  本轮 ui v0.4.0 就因此把 49 个 fix 写成了 73。项目自己文档里的数字
  （如 openspec 提案的「197 处注入」「443 画布对 1580 卡片」）可直接
  引用，但要在提案原文里核到那一行。
- 一篇至多一句情绪化语句；jixoai 是 neo-brutalist 不是 carnival —
  Tailwind 式粗口开场不适配，用 "It's done." 级冷句。
- 代码块即视觉：CLI/框架类每个亮点至少一个可复制块；mono 品牌下
  benchmark 输出与 `--help` 片段是天然素材；破坏性变用 diff 块。
- 坦承不完美（"mainly a maintenance release" 级诚实）比粉饰可信。
- 比喻克制（2026-09-07）：比喻=阅读成本。一篇至多一个、
  且只许出现在机制讲完后的定位句；主菜/赌注/接缝/同船/游戏房间这类
  行文比喻一律清除（craft.md D13，指标工具有计数）。
- 专有名词预算 + 大白话价值句（2026-09-07）：内部代号一篇
  一把、首次出现必须大白话释义，否则换成行为描述；API/包名/CLI/错误码
  是对象不是术语，照用。每个亮点先说"你现在能做什么/什么日常痛点消失
  了"，再讲机制（craft.md D14/D15）。
- 示例代码必要、过剩折叠（2026-09-07）：每个亮点至少一个
  可敲的示例；多了用 `<details><summary>示例：…</summary>` 折叠
  （.markdown-body details 已有样式）。示例只能来自 L1 release body、
  文中已链的 README/文档、或文章已断言的命令，不许发明 API（D16）。

## 内容权重（2026-09-07）

文章对正面与负面内容必须有别。版面占比 ≈ 对读者的决策价值：

1. **顺序**：新功能 → 破坏性变更 → 修复与其他。修复是负面内容。
2. **修复默认一句话**：`修复 <什么坏了>（<commit/PR 永链>）`，归入
   「其余变更」清单；不设小节、不叙事、不写动机段。反面教材：曾用
   1/3 篇幅讲一个 404 修复（opentray v0.21.1 文，后已纠正）。
3. **唯一例外**：hotfix release（该版本存在的唯一理由就是修复）→
   开头一句直陈 + 升级行即可，全文可以只有三段；但 patch 本就按
   重量级不发博客——能并入下一个 minor 叙事的就并入。
4. 流程/工程内容（发布自动化、CI 改造）按「新能力」对待，但同样
   受版面占比约束：它改变的是维护者的体验，不是用户的。

## 复核期的事实与口径（2026-09-11，ui v0.4.0 self review 沉淀）

定稿前必须单独走一遍「事实与口径」复核。指标门禁只管语气，管不了
下面的错；这五类每篇都要过。

1. **第三方库的版本声明不许转述**。仓库提案里写 upstream 的版本号时
   常常是转述，可能不准。ui v0.4.0 提案写「Svelte 5.57 ships the
   attachments API as a first-class syntax」，照抄进稿子就成了
   「Svelte 5.57 把 attachments 提升为一等语法」——查 svelte 官方
   CHANGELOG，attachments 自 **5.29.0** 起即为一等特性（feat, Minor），
   `fromAction` 落在 **5.32.0**，5.57.0 的 changelog 与 attachments
   毫无关系。这类错误会直接误导读者「必须升到 5.57」。规则：凡涉及
   第三方框架/库的版本、行为、API 契约，一律回上游 CHANGELOG/文档核实，
   核不到就不绑版本号，写能力本身（「attachments 已是一等语法，不用
   实验开关」）。
2. **破坏性变更的条数要写口径，且与 `!` 标记对账**。
   `git log A..B --pretty=%s | grep -E '^[a-z]+(\([^)]*\))?!:'` 给出的是
   **带 `!` 标记的提交数**，不等于读者要动手的**迁移动作数**。ui v0.4.0
   只有 1 个 `!`（`feat(system-dialog)!`，条目改名），但实际有三处迁移
   动作（特效挂载、条目改名、玻璃类退场）。两个数不一致时，正文必须
   挑明口径——写「三处迁移动作」并注明「只有改名那一个提交带 `!` 标记，
   另两处的破坏性写在各自的提案里」。**更别指望 L1 兜底**：GitHub
   Release 正文常常只有一行自动 changelog（ui v0.4.0 就是），不列变更。
3. **「新增 N」要区分净值与增量**。registry 既增又减时，标题的
   「新增 23 条」有歧义（实际新增 25、移除 `alert-dialog` 与 `icons`，
   净增 23）。写「净增 23 条」，正文给出 `113 → 136` 两端。
4. **每个数字都要能指到源，且算术自洽**。除了提案原文行（197 →
   「77 registry + 120 www mirror」；443/1580 → 「across 114 pages」），
   数字也可能只活在**提交主题**里：`398/398` 出自 `00d3fd92` 的
   「Suite 398/398 (+6 E2E, +3 scoping)」，registry.json 的描述字段里
   查不到。找不到源就删掉这个数字，不要留着。算术要能合上：类型分布
   写「41 feat、49 fix、66 docs，其余 19 个是 chore/test/重构」，
   41+49+66+19=175，读者不用回仓库就能验算。
5. **专有名词先 grep 仓库，再判断是不是自造比喻**。看着像 AI 比喻的
   中文词，可能正是项目自己的词汇：`皮肉`（flesh）、`方言`（dialect）、
   `主权契约`（sovereignty contract）、`验收裁定`（acceptance ruling）、
   `退场` 都在 ui 仓库的 openspec 与源码注释里。先
   `git grep -c '<词>' <tag>`，命中的保留；只有真自造的才按 craft.md D13
   清除。反过来也成立：清比喻时别把项目术语一起清掉。
6. **合并发布要逐条对账 CHANGELOG，且先于文风打磨（2026-09-13 实测）**。
   多个版本合并成一篇时，最容易漏的是**在某个版本里被单列、但不在主叙事
   线上**的能力点。opentray v0.27.1 合并五个版本，两轮文风打磨之后才想起来
   做对账，抓到两处真遗漏：0.25.0 的「overlay 安全区按 webview 投影」（还是
   Owner 亲自提的需求）、0.24.0 的「`{token}` 占位符对等由测试强制」。
   做法：把 `packages/*/CHANGELOG.md` 里每个版本的 bullet 抄成清单，用脚本
   查**核心名词**（如 `安全区` / `overlay` / `投影`）是否在稿里，缺失的逐条
   判定「该补」还是「刻意删」。**顺序是先对账再改文风**——文风定稿后再补
   事实，要重跑一遍语气门禁（本轮补完两段后顿号罗列从 2.44 涨到 2.74 触
   YELLOW 线 2.67，拆掉一个四连顿号才回落）。
7. **术语对齐：动笔前先读词汇源，别等写完再 grep**。
   Owner 退回 opentray v0.27.1 稿时的原话是「用词也不准确，你自己发明了
   很多词汇，而没有客观尊重使用 opentray 这套标准提供的最表面的词汇」。
   实测：稿里的 `有向连接`、`退场`、`轮转消费`、`异步端口`、`favicon`
   在仓库里全是 0 命中，而项目自己的说法（`定向直连`、`退役`、`公平轮转`、
   `异步上报通道`、`站点图标`）早就写在提案与词汇表里。**第 5 条只能救
   比喻，救不了这种系统性偏离**——偏离是「没读词汇表」造成的，不是
   「没 grep 单个词」造成的。按下面顺序读一遍再动笔：
   - `<repo>/i18n.zh.md` — 项目级中文领域词汇 SSOT，「用户表达 → 规范
     词汇 → 工程含义」三列表。**优先级最高**，先读这个。
   - `<repo>/packages/*/src/i18n/locales/zh-cn.ts` — UI 文案表。
     **「最表面的词汇」就在这里**：`advanced.addressBar` = 「导航工具栏」，
     它的 hint 本身就是一段可直接引用的中文产品说明（连按钮枚举
     「后退/前进/重载/地址栏」都写好了）。同文件还能确认向导里每个开关的
     官方叫法（「显示启动终端」「平滑缩放」「允许开发者模式」「打开应用」）。
   - `<repo>/packages/*/CHANGELOG.md` — 英文权威原文。中文译文以它为基准，
     不许转述（与第 1 条同源）。**版本能力的正式名称在这里**：0.25.0 的
     「Multi-webview window orchestration」「Toolbar carrier」、0.27.0 的
     「Extension EventPort」「16 ms window-event drain」。
   - `<repo>/openspec/changes/*/plans/plan.md` — 决策表。开头常有
     「用户语言系统：**『…』**」引文，那是 **Owner 自己说的词**，照用。
     决策描述也是现成的中文技术表述（`定向直连`、`多图层`、`统一事件族`、
     `公平轮转`、`涂绘原语`）。
   - `<repo>/openspec/changes/*/review/self-review.md` — 交付自查。含官方
     中文技术表述与验收口径（「16ms 轮询退役」「drained=12 与 tap 精确
     吻合」「代际隔离」「旧扩展零改动照常工作」）。**数字口径也在这里**，
     比转译 CHANGELOG 的英文更贴项目。
   - `<repo>/README-zh.md` 与 `<repo>/packages/website/src/lib/home-content.ts`
     — 官方中文 README 与官网文案。前者给产品定位与包名译法（「富弹出层
     扩展门面」「托盘持有的工具窗口」），后者是**语感参照**：短句、直给、
     名词短语做小标题、否定式直陈（「不是托盘图标，是入口」）。
   **坑一**：同一个概念在不同仓库可能用不同的词——`退场` 是 ui 仓库的词，
   opentray 用 `退役`；`排空` 在 opentray 0 命中，但 `drain 命令`、
   `drainWindowEvents 轮询` 是它的原生说法。一律按**目标仓库** grep，
   不要跨仓库搬运。
   **坑二**：保留英文原词也是「官方做法」，不都是没译。opentray 的
   `facade`、`carrier`、`broker`、`tap`、`drain`、`bridge` 在官方中文
   文档里就是英文（i18n.zh.md 写「facade 依赖闭包」），别自作主张译成
   「门面」「载体」。**判断法**：该词在 `i18n.zh.md` 与 self-review 里
   是英文 → 保留英文；是中文 → 用那个中文。
8. **API / flag / 字段名除了拼写，还要核「版本归属」（2026-09-13 实测）**。
   稿里出现的 flag、config 字段、API 名，先确认**它是哪个版本引入的**。
   opentray v0.27.1 稿把 `titleFollowsDocument` / `--no-title-follow` /
   `--icon-follow` 当破坏性变更写了进去，实际它们最早出现在 **0.22.0**
   （提交 `5cd2530b`），属于**上一篇博文**（v0.23.0 覆盖 0.22.0+0.23.0）的
   范围；而且这几个词在**所有 `packages/*/CHANGELOG.md` 里 0 命中**——从未
   被当作变更发布过。合并发布时这条尤其致命，因为「范围边界」正是本文的
   立身之本。判据三连：① 该词在目标版本的 CHANGELOG 里有没有；
   ② `git tag --contains <commit>` 落在哪个 tag；③ 上一篇稿有没有讲过
   （grep 前一篇）。三条都不支持就**删掉**——别因为「上一篇没讲过」就留下，
   本文不是补漏，是讲这几个版本。
9. **风格由 Owner 点单，changelog 风格是首选默认（Owner 指令 2026-09-16）**。
   动笔前必须问一次文章风格（SKILL.md Workflow 第 4 步），第一选项：
   「用 changelog 的风格、客观且直观、通俗易懂且准确，无晦涩词汇和
   比喻」。首例即 opentray v0.27 系列文（2026-09-16-opentray-v0-27）：
   Owner 先退回叙事稿（「用词也不准确，你自己发明了很多词汇」），随后
   明确定调 changelog 风格并要求其成为默认。该风格下的写法要点：
   - 按主题分节（不是按版本分段），节内陈述「改了什么/为什么/可观察
     行为」，数字直接给（121→0、1000/1MiB、300 ms）。
   - 不写背景弧、不写动机铺陈、不设悬念；每一句都是可核查的事实。
   - 枚举优先用项目官方写法：UI 枚举与多语言列表用斜杠（「后退/
     前进/重载/地址栏」——zh-cn.ts 的 hint 原文如此），代码标识符
     之间用半角逗号（`urlChange`, `titleChange`, `focused`）。
   - 术语纪律不变：第 7 条词汇源照读；changelog 风格不豁免术语对齐。
   - 语气门禁照跑；顿号罗列超线时按官方斜杠写法收敛，不为指标删事实。
