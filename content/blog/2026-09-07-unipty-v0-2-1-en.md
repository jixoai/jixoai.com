UniPty v0.2.1 is out (GitHub Release cut at 2026-09-07 12:21 UTC). This
version lets the Node side swap its PTY engine for the first time: the new
official Backend package `@unipty/backend-zigpty` brings in zigpty, a
Zig-built engine. Install one package, change the one line that creates
your Backend, and your application code runs unchanged.
`@unipty/backend-zigpty@0.2.0` hit npm at 12:21 UTC; the GitHub Release was
cut within the same minute.

## Why Node can swap engines now

UniPty's Node route has always run on node-pty (distributed through the
`@lydell/node-pty` prebuilds). Its binaries live in per-platform
sub-packages installed via optionalDependencies, so what ends up on a given
machine depends on how the installer treats optional dependencies: the
install posture decides, not your code. When something broke, there was no
second option. You went back and fixed the install environment.

Since the v1 architecture proposal in 2026-08, UniPty has treated engines as
explicit replaceable parts: Core owns every observable behaviour, you inject
the chosen Backend into `new UniPty({ backend })`, and the registry is keyed
by engine identity rather than runtime, so one runtime can host several
engines. The design always allowed it; only one engine was ever installable.
v0.2.1 adds zigpty, the first real instance of several engines under one
runtime. The release catalog (the evidence table behind the compatibility
page) upgraded its aggregation in step, validating package name and engine
identity together per route
([f083127](https://github.com/jixoai/unipty/commit/f083127)), so the two
Node engines cannot stand in for each other.

## zigpty: an engine that installs complete

[zigpty](https://github.com/pithings/zigpty) (npm `zigpty@0.2.1`, MIT,
maintained by [pi0](https://github.com/pi0)) implements a cross-platform PTY
in Zig and exposes it to Node through NAPI bindings. For users, its most
tangible property is the distribution model:

| Dimension | zigpty's answer |
| --- | --- |
| Runtime dependencies | 0 |
| Prebuild coverage | 8 platform tuples (linux/macos/windows × x64/arm64, glibc and musl) |
| Distribution | every prebuild ships inside the npm tarball, ~420KB unpacked |
| Install scripts | none; node-gyp is never touched |

For comparison: `@lydell/node-pty` puts its prebuilds in per-platform
sub-packages installed through optionalDependencies; the Bun and Deno routes
rely on runtime built-ins or vendored dynamic libraries; zigpty packs all 8
platform tuples into the main package, installs complete, and no
`--omit=optional` posture can break it. Installing is one line:

```bash
npm install unipty @unipty/backend-zigpty
```

One upstream behaviour deserves care: when a prebuild fails to load, the
zigpty library silently falls back to a pipe-based pseudo-PTY, and isatty
and kernel-level geometry both fail on the pseudo variant. UniPty's adapter
hard-gates that fallback at readiness; if `hasNative` is not true you get
`unsupported`, never a fake PTY standing in for a real one.

## Swapping engines is a one-line change

For a project already on unipty, adopting zigpty touches exactly the line
that creates the Backend:

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

Everything after the factory call is the familiar contract. `spawn` takes
structured argv, `write()` returns boolean readiness, `close()` and
`terminate()` are idempotent and never cascade, and `exited` is an
independent, repeatable promise. Swap the engine, keep the semantics. The
25-scenario public contract suite ran in full against the installed package
artifact: one native evidence record on local darwin-arm64, plus one each
from CI ubuntu and macos, all in the
[release catalog](https://unipty.jixoai.com/compatibility).

## Two pitfalls we hit while integrating

A new engine never lands clean on the first try. This route fixed two real
pitfalls before release; the package you install today has neither.

The first lived on ubuntu: when a child exits very fast, its output could
vanish. zigpty's exit callback destroys the read stream synchronously with
no flush, so buffered data never made it out. The adapter now repossesses
the stream inside the exit window, and the final output reaches you whole
([3d56f71](https://github.com/jixoai/unipty/commit/3d56f71)).

The second hid inside `writeDecode`: a write rejected for backpressure had
already advanced decoder state, so retrying the same bytes could produce a
different result. The fix splits admission from decoding: byte values enter
the queue raw and decode only at pump time, so a rejected value retried
decodes byte-identically
([f083127](https://github.com/jixoai/unipty/commit/f083127)).

Neither problem was visible in the shape of the public API; only running
the real contract suite exposed them. That is why UniPty insists on full
contract evidence.

## Four things to know before you adopt it

Engines have real differences. All four points below live in the
[capability matrix in the README](https://github.com/jixoai/unipty/blob/v0.2.1/README.md#capability-differences-what-the-engines-actually-give-you);
they are worth a pass before you swap.

**1. Writes are text-native.** zigpty's `write` accepts strings only, so the
Endpoint rejects byte input with `unsupported` by default. If your input is
bytes (an xterm.js front end, protocol forwarding, that kind of consumer),
one option fixes it:

```ts
const backend = await createZigptyBackend({ writeDecode: true });

// byte input is now legal: decoded through a stateful streaming decoder,
// so multibyte sequences split across chunks are safe
pty.write(new TextEncoder().encode("echo héllo\r"));
```

`writeDecode` is the Backend-owned convenience; fatal decode policies reject
the whole value instead of replacing it with garbage. Its decode path is the
one that got the atomicity fix above.

**2. Windows fails closed.** zigpty ships a ConPTY prebuild, but its
`pause()` / `resume()` are no-ops on win32, which would leave output
backpressure with nowhere to propagate. The adapter therefore refuses
readiness on Windows and narrows the metadata targets to darwin and linux.
The gate lifts only with real Windows contract evidence.

**3. Transport EOF is repossessed, not given.** The engine exposes no
transport-layer events. The adapter takes over the master-side stream inside
the exit window and uses its real `end` / `close` as EOF, with a 50ms
quiescence window as fallback (late chunks extend the window, so trailing
output is never cut). The cost: on this route a transport read error is
indistinguishable from clean EOF, a declared limitation. The repossession is
exactly the fix for the first pitfall above.

**4. The exit observation has its own shape.** A signalled death reports
`{ exitCode: 0, signal: "SIGTERM" }`; the exit code stays exactly what the
engine reported rather than a fabricated null. A missing executable is an
exit observation of `{ exitCode: 1, signal: null }`, never a spawn exception.

## Upgrading

No breaking changes. The zigpty route is a purely additive package; Core and
the existing three routes are untouched. The Backend package's npm version
is 0.2.0; that is the number to install:

```bash
npm i @unipty/backend-zigpty@0.2.0
```

If you are already on `unipty@0.2.0`, Core needs nothing.
