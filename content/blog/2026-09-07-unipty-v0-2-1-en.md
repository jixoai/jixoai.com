UniPty v0.2.1 is out (GitHub Release cut at 2026-09-07 12:21 UTC). It adds
one official Backend package, `@unipty/backend-zigpty`, backed by
[zigpty](https://github.com/pithings/zigpty) (npm `zigpty@0.2.1`, MIT,
maintained by pi0), a PTY engine written in Zig. Node now has two engines to
choose from; the other one is the existing `@unipty/backend-node-pty`.

## zigpty vs node-pty

The two routes share the same public contract; every difference lives in
the engine layer. For choosing between them, the main facts are below.

| Dimension | zigpty | node-pty (@lydell distribution) |
| --- | --- | --- |
| Runtime dependencies | 0 | platform sub-packages (optionalDependencies) |
| Install scripts | none | none |
| Distribution | prebuilds for all 8 platform tuples inside the main tarball, ~420KB | one sub-package per platform, installed per platform |
| Install robustness | unaffected by `--omit=optional` and similar postures | breaks when optional dependencies are skipped |
| Native text output | yes (`encoding: "utf8"`) | yes (`encoding: "utf8"`) |
| Byte writes | rejected by default; needs the `writeDecode` option | accepted by default |
| Windows | route unavailable for now (upstream supports it; see below) | declared, evidence-gated |
| Transport read errors surfaced | indistinguishable (see below) | surfaced as `unsupported` |

zigpty's advantage is distribution: no runtime dependencies, no platform
sub-packages, all prebuilds in the main package. What you install is what
you get, regardless of how the installer treats optional dependencies. That
is more robust in environments you do not control (restricted CI, offline
mirrors).

The costs are in the caveats below: byte writes need an extra option, and
Windows is unavailable for now. If either matters to your case, the node-pty
route remains the more direct choice.

## Usage

```bash
npm install unipty @unipty/backend-zigpty
```

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

`spawn`, `stream`, `write`, `resize`, `close`, `terminate`, and `exited`
behave identically to the other three routes. The 25-scenario public
contract suite ran in full against the installed package artifact: one
native evidence record on local darwin-arm64, plus one each from CI ubuntu
and macos, all in the [release catalog](https://unipty.jixoai.com/compatibility).

## Caveats

The full difference surface is the
[capability matrix in the README](https://github.com/jixoai/unipty/blob/v0.2.1/README.md#capability-differences-what-the-engines-actually-give-you).
Four things to know up front are listed below.

1. **Byte writes need an option.** The engine's `write` accepts strings
only, so the Endpoint rejects byte input with `unsupported` by default. For
byte input streams (an xterm.js front end and the like), enable
`writeDecode`; the decoding is stateful and safe across chunk splits:

```ts
const backend = await createZigptyBackend({ writeDecode: true });
pty.write(new TextEncoder().encode("echo hi\r"));
```

2. **The route is unavailable on Windows for now.** zigpty itself
supports Windows (the prebuilds are all there), but its Windows
implementation's `pause()` / `resume()` are empty methods (zigpty 0.2.1's
`WindowsPty`), so output backpressure cannot propagate. The adapter
therefore reports `unsupported` on Windows and narrows the metadata targets
to darwin and linux; the gate lifts once upstream adds flow control and
contract evidence exists.

   > Update (v0.2.2): this was rewritten along the adapter path instead — the
   > route now runs on Windows with declared buffering semantics, memory is
   > bounded by the disk-backed `outputSpool` option; see the
   > [next post](/blog/2026-09-07-unipty-v0-2-2-en/).

3. **Transport read errors are indistinguishable.** The engine exposes no
transport-layer events. The adapter repossesses the read stream inside the
exit window, uses its real `end` / `close` as EOF, and keeps a 50ms
quiescence window as fallback. A read error cannot be distinguished from
clean EOF on this route; that is a declared limitation.

4. **Exit shapes.** A signalled death reports
`{ exitCode: 0, signal: "SIGTERM" }` (the exit code keeps the engine's
original value); a missing executable reports `{ exitCode: 1, signal: null }`
as an exit observation, not an exception.

## Upgrading

No breaking changes; purely additive. The Backend package's npm version is
0.2.0:

```bash
npm i @unipty/backend-zigpty@0.2.0
```

If you are already on `unipty@0.2.0`, Core needs nothing.
