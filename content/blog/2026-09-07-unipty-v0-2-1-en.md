UniPty v0.2.1 is out (GitHub Release cut at 2026-09-07 12:21 UTC). The main
course is a fourth official Backend route, `@unipty/backend-zigpty`: for the
first time a Node project can swap its PTY engine away from `node-pty`
without touching a single line of application code.

## Why Node can have a second route

UniPty's route registry is keyed by substrate identity, not by runtime. A
route is one concrete engine plus its honestly declared capability surface;
the runtime is just a field in that declaration. Until v0.2.1 this was
theory. Now it has its first instance: under the same Node runtime,
`node-pty` and `zigpty` are two independent routes, each producing its own
verification evidence, each gated separately at release time. The gate
itself was upgraded in this release: catalog aggregation now validates a
`package name + backend id` pair per route, so the two Node routes cannot
stand in for each other ([f083127](https://github.com/jixoai/unipty/commit/f083127)).

## What kind of engine zigpty is

[zigpty](https://github.com/pithings/zigpty) (npm `zigpty@0.2.1`, MIT,
maintained by [pi0](https://github.com/pi0)) implements a cross-platform PTY
in Zig and exposes it to Node through NAPI bindings. What matters most to
users is the distribution model:

| Dimension | zigpty's answer |
| --- | --- |
| Runtime dependencies | 0 |
| Prebuild coverage | 8 platform tuples (linux/macos/windows × x64/arm64, glibc and musl) |
| Distribution | every prebuild ships inside the npm tarball, ~420KB unpacked |
| Install scripts | none; node-gyp is never touched |

For comparison: `@lydell/node-pty` distributes through per-platform
sub-packages (optionalDependencies), while Bun and Deno rely on runtime
built-ins or vendored dynamic libraries. zigpty is install-and-done; an
`--omit=optional` install posture cannot break it.

There is one more design decision we appreciate. When a prebuild fails to
load, the upstream library silently falls back to a pipe-based pseudo-PTY.
UniPty's adapter hard-gates that fallback at readiness: if `hasNative` is
false you get `unsupported`, never a fake PTY standing in for a real one
(isatty and kernel-level geometry both fail on the pseudo variant).

## How to use it

Install, swap one factory call, and everything else is identical to the
other three routes:

```bash
npm install unipty @unipty/backend-zigpty
```

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

`spawn` is still structured argv, `write()` still returns boolean readiness,
`close()` and `terminate()` still never cascade, and `exited` is still an
independent, repeatable promise. The 25-scenario public contract suite ran
in full against the installed package artifact: one native evidence record
on local darwin-arm64, plus one each from CI ubuntu and macos, all in the
[release catalog](https://unipty.jixoai.com/compatibility).

## Four things to know before you adopt it

All four live in the [capability matrix in the README](https://github.com/jixoai/unipty/blob/v0.2.1/README.md#capability-differences-what-the-engines-actually-give-you);
these are the ones you need before writing code:

**1. Writes are text-native.** zigpty's `write` accepts strings only, so the
Endpoint rejects byte input with `unsupported` by default. If your input is
bytes (an xterm.js front end, protocol forwarding, that kind of consumer),
one option fixes it:

```ts
const backend = await createZigptyBackend({ writeDecode: true });

// byte input is now legal: decoded through a stateful streaming decoder,
// so multibyte sequences split across chunks are safe
pty.write(new TextEncoder().encode("echo héllo\r"));
```

`writeDecode` is the Backend-owned convenience; fatal decode policies reject
the whole value instead of replacing it with garbage.

**2. Windows fails closed.** zigpty ships a ConPTY prebuild, but its
`pause()` / `resume()` are no-ops on win32, which would leave output
backpressure with nowhere to propagate. The adapter therefore refuses
readiness on Windows and narrows the metadata targets to darwin and linux.
The gate lifts only with real Windows contract evidence.

**3. Transport EOF is repossessed, not given.** The engine exposes no
transport-layer events. The adapter takes over the master-side stream inside
the exit window and uses its real `end` / `close` as EOF, with a 50ms
quiescence window as fallback (late chunks extend the window, so trailing
output is never cut). The cost: on this route a transport read error is
indistinguishable from clean EOF. That is a declared limitation, not an
undocumented one.

**4. The exit observation has its own shape.** A signalled death reports
`{ exitCode: 0, signal: "SIGTERM" }`; the exit code stays exactly what the
engine reported rather than a fabricated null. A missing executable is an
exit observation of `{ exitCode: 1, signal: null }`, never a spawn exception.

## Other changes

- Fixed fast-exit children losing their output on ubuntu: zigpty's exit
  callback destroys the read stream synchronously with no flush, so the
  adapter now repossesses the stream inside the exit window
  ([3d56f71](https://github.com/jixoai/unipty/commit/3d56f71))
- Fixed writeDecode saturation rejection advancing decoder state: byte
  values are now admitted raw and decoded at pump time, so a rejected value
  retried decodes byte-identically
  ([f083127](https://github.com/jixoai/unipty/commit/f083127))
- Release catalog registry re-keyed by route identity with dual
  package-plus-backend-id validation
  ([b878ce4](https://github.com/jixoai/unipty/commit/b878ce4),
  [f083127](https://github.com/jixoai/unipty/commit/f083127))
- Documentation synced repo-wide for the fourth route: bilingual READMEs,
  architecture doc, contributing guide, and the docs site
  ([021a82d](https://github.com/jixoai/unipty/commit/021a82d))

Full list in [compare v0.2.0...v0.2.1](https://github.com/jixoai/unipty/compare/v0.2.0...v0.2.1).

## Upgrading

No breaking changes. The zigpty route is a purely additive package; Core and
the existing three routes are untouched:

```bash
npm i @unipty/backend-zigpty@0.2.0
```

If you are already on `unipty@0.2.0`, Core needs nothing.
