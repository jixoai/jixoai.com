OpenIWeb v0.1.0 is out (2026-09-06, the first public cut). One-line positioning: **an open-source personal application node for people who don't want to learn containers, databases, or network operations** — hand the MCP endpoint and a single key to an AI coding agent (Codex, Claude Code, …) and applications deploy and run on your own node; you manage everything from a browser console with one key.

## Background: self-hosting is too hard for most people, and the labor has changed

Running a few personal apps on your own server today means learning containers, databases, reverse proxies, and network operations — or surrendering your data to someone's PaaS. Meanwhile, AI coding agents can already do most deployment and operations work; what they lack is a **controlled entry**: an endpoint, a key, and a clear boundary.

OpenIWeb answers both with one architecture. And its security bottom line precedes its features: application code may be copied from the internet or generated by AI, so it is **untrusted by default** — isolating every application from the node control plane and from each other is the product's security bottom line, not an add-on.

## A single-port Rust kernel: one installation, one entry

`kernel-rs` (~4MB static binary) is the node's **only published port** (`:8080`): host routing, recovery authority, owner-key auth, and a per-app proxy with WebSocket upgrade tunnels. Everything else — RustFS, the control API, every celld listener — stays on container-internal loopback and is never published:

```text
public Internet
      |
iweb-kernel :8080           the only published port (a single Rust binary)
  +-- api.<base>                  -> Kernel control API (same router/auth as loopback)
  +-- admin.<base>                -> per-app celld :8787 (Admin console)
  +-- mcp.<base>/mcp              -> per-app celld :8797 (MCP endpoint)
  +-- <app>.<base>                -> per-app celld (IWEB_CELLD_PORTS)
  +-- <base>/<app>/app            -> path alias for the same application
                                      |
              RustFS (S3-compatible, loopback-only, no console)
                                      |
          iweb-workspace / iweb-cells-<app> / iweb-apps / iweb-system
```

TLS is terminated in front of the node (1Panel, Caddy, nginx, …); the kernel routes by HTTP `Host` header only. The whole node's idle memory envelope is **≤ 240 MB RssAnon** — a boundary written into the spec ([`openspec/specs/node-boundary/`](https://github.com/jixoai/openiweb/tree/v0.1.0/openspec/specs/node-boundary)), not a marketing number.

## The MCP operations surface: every request carries a key

`mcp.<base>/mcp` is a protected system application: **every** JSON-RPC request — including `initialize` and `tools/list` — must carry an owner key as a Bearer token. Tools cover workspace read/write/delete and domain listing/registration; the worker forwards the credential per request and never stores it. Wiring an AI agent in is one standard MCP config:

```json
{ "mcpServers": { "OpenIWeb": { "url": "https://mcp.<base>/mcp",
  "headers": { "Authorization": "Bearer <owner-key>" } } } }
```

## A two-tier trust runtime: untrusted code runs inside the engine's cage

Applications split into two tiers, matching two kinds of trust:

- The **trusted tier**, [celld](https://github.com/denoland/celld) v0.3 (Cloudflare Workers API): image-seeded fleet apps, one process per app, watchdog soft limits — the console and the demo apps live here.
- The **untrusted tier**, iweb-wasmd (Wasmtime, wasi:http 0.2 components): **the only runtime admission path** — engine-enforced isolation, host services, no socket capability. Apps copied from the web or generated by AI enter here.

Object storage is built-in RustFS (S3-compatible, MinIO lineage, single-node friendly, loopback-only with no console), four buckets each in their lane: `iweb-workspace`, `iweb-cells-<app>`, `iweb-apps`, `iweb-system`.

## Revocable owner keys: one identity, many keys

The GitHub PAT model: delegated keys (`iwb_<id>_<secret>`) carry absolute expiry; the console copies a **ready-to-paste deployment prompt** (MCP endpoint and key included) straight into an AI agent's hands; a ban is instant (in-flight monitor sockets close; new requests get 401); an append-only, per-key-attributed audit trail records every control-plane operation — **including rejected attempts**.

The bootstrap `IWEB_API_TOKEN` always authorizes and cannot be banned: it is the credential face of the `api.<base>` recovery law — even if every delegated key and the Admin app are compromised, the owner can still reach the Kernel control API directly.

## The rest (and an honest limitations list)

- **Static console**: a SvelteKit + shadcn-svelte static app served as celld native assets — replaceable like any app; never a secret configuration screen
- **Three demo applications**: `hello` (pure static via celld assets), `search` (D1/SQLite search with parameterized SQL), `collab` (two celld instances sharing one Durable Object for cross-instance realtime collaboration over WebSocket)
- Test chassis: 489 bun tests + the Rust battery (cargo test / clippy) + the kernel-recovery black-box contract suite

Known limitations at v0.1.0, stated plainly: TLS/wildcard certificates are a deployment concern (the kernel does HTTP Host-routing inside the container); monitor metrics are per-Kernel-lifecycle, not durable history; `notes` is deployed but not routed; wasm publication stays fail-closed (no celld publication exists — image-only supply).

## Install (first release, nothing to upgrade from)

This release ships as a source-built container image (no registry image published). Build from the tag:

```bash
git clone https://github.com/jixoai/openiweb.git && cd openiweb
git checkout v0.1.0
cp .env.example .env   # set CELLD_NODE, IWEB_BASE_HOST, a long random IWEB_API_TOKEN, and the S3 secrets
docker compose up -d --build
curl -H "Host: $IWEB_BASE_HOST" http://127.0.0.1:9010/_iweb/health
```

Multi-arch: `Dockerfile` (arm64) and `Dockerfile.amd64` (x86_64, with `CARGO_BUILD_JOBS` and `CRATES_MIRROR=rsproxy` builder knobs for constrained hosts). Upgrading later = rebuild the image from the new tag and recreate the container; node data lives in the `iweb-data` volume and RustFS buckets, configuration lives in `.env`; owner keys are issued by the Kernel/console and revocable from the console — secrets are never stored in the workspace.
