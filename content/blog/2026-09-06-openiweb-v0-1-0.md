OpenIWeb v0.1.0 发布了（2026-09-06，第一个公开版本）。它是**面向普通人的开源个人应用节点**：你不需要理解容器、数据库或网络运维；把 MCP 端点和一把密钥交给 AI 编程代理（Codex、Claude Code……），应用就部署和运行在你自己的节点上；你用一个浏览器控制台和一把密钥管理一切。

## 背景：自托管对普通人太难，而运维劳动力已经变了

想在个人服务器上跑几个自己的应用，今天要么把整套运维课学一遍，从容器、数据库到反向代理和网络运维；要么把数据交给别人的 PaaS。AI 编程代理则已经能干大部分部署与运维的活，缺的只是一个**受控的入口**：一个端点、一把钥匙和一个明确的边界。

OpenIWeb 对这两件事的回答是同一套架构。而它的安全底线先于功能存在：应用代码可能来自网络复制或 AI 生成，因此**默认不可信**。把每个应用与节点控制面、与其他应用隔离开，就是这个底线本身，不是附加项。

## 单端口 Rust 内核：一台安装，一个入口

`kernel-rs`（约 4MB 的静态二进制）是全节点**唯一发布的端口**（`:8080`），承担 Host 路由、恢复权威与 owner-key 鉴权，并为每个应用代理流量（带 WebSocket 升级隧道）。其余一切（RustFS、控制 API 与每个 celld 的监听）全部留在容器内回环，绝不发布：

```text
公网
  |
iweb-kernel :8080           唯一发布端口（单个 Rust 静态二进制）
  +-- api.<base>                  -> Kernel 控制 API（与回环监听同鉴权）
  +-- admin.<base>                -> 独立 celld :8787（管理控制台）
  +-- mcp.<base>/mcp              -> 独立 celld :8797（MCP 端点）
  +-- <app>.<base>                -> 各应用独立 celld（IWEB_CELLD_PORTS）
  +-- <base>/<app>/app            -> 同一应用的路径别名
                                      |
                    RustFS（S3 兼容，仅回环，不开 console）
                                      |
                  iweb-workspace / iweb-cells-<app> / iweb-apps / iweb-system
```

TLS 在节点前置层终止（1Panel、Caddy 或 nginx），内核只按 HTTP `Host` 头路由。整节点的闲时内存封套是 **≤ 240 MB RssAnon**。这条边界写在规格里（[`openspec/specs/node-boundary/`](https://github.com/jixoai/openiweb/tree/v0.1.0/openspec/specs/node-boundary)），不是营销数字。

## MCP 运维面：每个请求都要带钥匙

`mcp.<base>/mcp` 是一个受保护的系统应用：**每个** JSON-RPC 请求（包括 `initialize` 和 `tools/list`）都必须携带 owner key 作为 Bearer token。工具覆盖 workspace 读写删除与域名列出/注册；worker 逐请求转发凭据、永不存储。AI 代理的接入就是一段标准的 MCP 配置：

```json
{ "mcpServers": { "OpenIWeb": { "url": "https://mcp.<base>/mcp",
  "headers": { "Authorization": "Bearer <owner-key>" } } } }
```

## 两层信任运行时：不可信代码跑在引擎的笼子里

应用分两层，对应两种信任。

- **信任层** [celld](https://github.com/denoland/celld) v0.3（Cloudflare Workers API）：舰队应用由镜像种子提供，每应用独立进程，看门狗只设软限。控制台与演示应用住在这里。
- **不可信层** iweb-wasmd（Wasmtime，wasi:http 0.2 组件）是**唯一的运行时准入路径**：引擎内强制隔离，只有宿主服务，没有 socket 能力。从网上抄来的或 AI 生成的应用，从这里进入。

对象存储内置 RustFS（S3 兼容，MinIO 血统，单节点友好，仅回环不开 console），四个桶各司其职：`iweb-workspace` · `iweb-cells-<app>` · `iweb-apps` · `iweb-system`。

## 可吊销的 owner 密钥：一个身份，多把钥匙

GitHub PAT 的模型：委托密钥（`iwb_<id>_<secret>`）带绝对过期；控制台可一键复制一段**开箱即用的中文部署提示词**（含 MCP 端点与密钥）直接交给 AI 代理；封禁即时生效（在途监控 socket 关闭、新请求 401）；append-only 的审计流按密钥归因记录每一次控制面操作，**被拒绝的尝试也在内**。

bootstrap `IWEB_API_TOKEN` 永远有效、不可封禁：它是 `api.<base>` 恢复法则的凭据面。即使每把委托密钥连同 Admin 应用全部沦陷，owner 仍然可以直接触达 Kernel 控制 API。

## 其余大盘（与诚实的限制清单）

- **静态控制台**：SvelteKit + shadcn-svelte 静态应用，以 celld 原生资产服务，像任何应用一样可替换，永远不是密钥配置界面
- **三个演示应用**：`hello`（celld assets 纯静态）、`search`（D1/SQLite 参数化 SQL 搜索）、`collab`（两个 celld 实例共享一个 Durable Object，跨实例 WebSocket 实时协作）
- 测试底盘：bun 全量 489 测 + Rust battery（cargo test / clippy）+ kernel-recovery 黑盒契约套件

v0.1.0 的已知限制（照实说）：TLS/通配符证书是部署侧的事（内核在容器内做 HTTP Host 路由）；监控指标随 Kernel 生命周期、非持久历史；`notes` 已部署但未路由；wasm 发布保持 fail-closed（celld 侧发布尚不存在，只有镜像供应）。

## 安装（首版，无升级路径）

本版以源码构建容器镜像分发（未发布 registry 镜像）。从 tag 构建：

```bash
git clone https://github.com/jixoai/openiweb.git && cd openiweb
git checkout v0.1.0
cp .env.example .env   # 设置 CELLD_NODE、IWEB_BASE_HOST、足够长的随机 IWEB_API_TOKEN、S3 凭据
docker compose up -d --build
curl -H "Host: $IWEB_BASE_HOST" http://127.0.0.1:9010/_iweb/health
```

多架构：`Dockerfile`（arm64）与 `Dockerfile.amd64`（x86_64；受限主机可用 `CARGO_BUILD_JOBS` 与 `CRATES_MIRROR=rsproxy` 构建旋钮）。后续版本的升级 = 从新 tag 重建镜像并重建容器；节点数据住在 `iweb-data` 卷与 RustFS 桶，配置住在 `.env`；owner 密钥由 Kernel/控制台签发、控制台可吊销，密钥永不落 workspace。
