The zigpty route took two steps today (2026-09-07). Midday v0.2.1 (2026-09-07 12:21 UTC) added it to the official route set, giving Node a second engine choice beyond node-pty for the first time; evening v0.2.2 (2026-09-07 20:53 UTC) removed its Windows readiness gate and added a disk-backed output buffer. Together the two releases touch exactly one new package; Core and the other three routes are untouched. This post tells both steps as one story.

## Why zigpty

The engine is [zigpty](https://github.com/pithings/zigpty) (npm `zigpty@0.2.1`, MIT, maintained by pi0), a cross-platform PTY implementation in Zig exposed to Node through NAPI bindings. What earned it the fourth route is the distribution model. The two Node routes share one public contract; the differences are all at the engine level, and the table below is the honest selection surface.

| Dimension | zigpty | node-pty (@lydell distribution) |
| --- | --- | --- |
| Runtime dependencies | 0 | platform sub-packages (optionalDependencies) |
| Install scripts | none | none |
| Distribution | prebuilds for 8 platform tuples in the main tarball, ~420KB | one sub-package per platform, installed per host |
| Install robustness | `--omit=optional` and similar postures change nothing | optional deps skipped means not installed |
| Native text output | yes (`encoding: "utf8"`) | yes (`encoding: "utf8"`) |
| Byte writes | rejected by default, needs `writeDecode` | accepted by default |
| Windows | runs, buffered output (since v0.2.2; see below) | declared, evidence-gated |
| Transport read errors surfaced | indistinguishable (see below) | surfaced as `unsupported` |

zigpty's advantage is distribution: no runtime dependencies, no platform sub-packages, all prebuilds in the main package. What you install is what you get, regardless of how the installer treats optional dependencies. That is more robust in environments you do not control (restricted CI, offline mirrors). The costs are the extra option for byte writes and the buffered output shape on Windows, both covered below.

One upstream behavior to watch: when a prebuild cannot load, the zigpty library silently falls back to a pipe-based pseudo-PTY, where isatty and kernel geometry both fail. The adapter hard-gates that fallback at readiness; `hasNative` false means `unsupported`, never a fake PTY.

## Usage

```bash
npm install unipty @unipty/backend-zigpty
```

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

`spawn`, `stream`, `write`, `resize`, `close`, `terminate`, and `exited` behave identically to the other three routes; swapping engines does not swap semantics. The 25-scenario public contract suite ran in full against the installed package artifact in both releases: one native evidence record on local darwin-arm64, plus one each from CI ubuntu and macos, all in the [release catalog](https://unipty.jixoai.com/compatibility).

## Windows: from a gate to an adapter

When v0.2.1 introduced this route, it failed closed on Windows: the engine ships complete ConPTY prebuilds, but its Windows `pause()` / `resume()` are empty methods (zigpty 0.2.1's `WindowsPty`), so consumer-paced output backpressure cannot reach the kernel. The adapter refused readiness rather than run with a queue that grows without bound. The lift condition we wrote down was "upstream adds flow control".

v0.2.2 stops waiting. UniPty cannot discipline every engine; third-party developers will bring their own backends, and bridging engine differences in adapter code is precisely the point of this architecture. With the gate removed, the route runs on Windows as-is: the adapter keeps draining engine callbacks, and the cost is declared honestly as "output backpressure does not reach the kernel on this platform", the same declared-limitation class the Deno route applies to its internal reader thread. No platform branch is needed anywhere:

```ts
const backend = await createZigptyBackend(); // same line on Windows and unix
```

Support claims stay evidence-gated. Windows tuples remain declared-unverified until public contract evidence exists; the [compatibility catalog](https://unipty.jixoai.com/compatibility) presents them as such. Removing the gate is not a claim of verified support.

## outputSpool: a disk-backed output buffer

A stalled consumer is the main memory risk. A terminal attached to a browser tab that the user switches away from for ten minutes produces ten minutes of output with nowhere to go, piling up in the adapter's queue. Outside Windows the same problem exists; unix kernel backpressure just hands the pressure back to the child, so the pile grows slowly.

`outputSpool` replaces that queue with a disk-backed FIFO:

```ts
const backend = await createZigptyBackend({
  outputSpool: { memoryBytes: 4 * 1024 * 1024 }, // or just `true` for defaults
});
```

The mechanism has three parts. The in-memory head is capped at 1 MiB by default; records beyond it spill to one adapter-owned temp file; replay follows the consumer's pull pace strictly, never enqueuing past the stream's water mark. The public stream is byte-identical with and without the spool: text records round-trip per complete record and chunk boundaries are preserved. When the child exits, the completion signal waits for the backlog to drain, so a fast-exit tail is never cut by EOF; an explicit `close()` still completes synchronously and deletes the temp file.

Three boundaries to know before enabling it. Spill IO is synchronous; disk usage while backlogged is unbounded by design, bounded only by the child's own output; an abruptly-killed process leaves the temp file to OS tmp reaping. On platforms where the engine can pause (unix), passing the memory bound also propagates pressure back into the kernel, blocking the child instead of piling higher.

## Caveats

The full difference surface is the
[capability matrix in the README](https://github.com/jixoai/unipty/blob/v0.2.2/README.md#capability-differences-what-the-engines-actually-give-you).
Beyond the two sections above, three things to know up front.

1. **Byte writes need an option.** The engine's `write` accepts strings
only, so the Endpoint rejects byte input with `unsupported` by default. For
byte input streams (an xterm.js front end and the like), enable
`writeDecode`; the decoding is stateful and safe across chunk splits:

```ts
const backend = await createZigptyBackend({ writeDecode: true });
pty.write(new TextEncoder().encode("echo hi\r"));
```

2. **Transport read errors are indistinguishable.** The engine exposes no
transport-layer events. The adapter repossesses the read stream inside the
exit window, uses its real `end` / `close` as EOF, and keeps a 50ms
quiescence window as fallback. A read error cannot be distinguished from
clean EOF on this route; that is a declared limitation.

3. **Exit shapes.** A signalled death reports
`{ exitCode: 0, signal: "SIGTERM" }` (the exit code keeps the engine's
original value); a missing executable reports `{ exitCode: 1, signal: null }`
as an exit observation, not an exception.

## Upgrading

The npm package version sits one step behind the GitHub tag (tag v0.2.1 shipped package 0.2.0; tag v0.2.2 shipped package 0.2.1); install by the npm version:

```bash
npm i @unipty/backend-zigpty@0.2.1
```

`outputSpool` is off by default; without it, behavior is byte-identical to 0.2.0. If you are already on `unipty@0.2.0`, Core needs nothing.
