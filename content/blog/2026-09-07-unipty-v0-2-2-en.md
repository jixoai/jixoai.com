UniPty v0.2.2 is out (GitHub Release cut at 2026-09-07 20:53 UTC). One package changes: `@unipty/backend-zigpty` moves to 0.2.1 with two things at its core. The zigpty route now runs on Windows instead of refusing readiness, and output gains an optional disk-backed buffer, `outputSpool`. Core and the other three routes are untouched.

## Windows: from a gate to an adapter

When [v0.2.1](/blog/2026-09-07-unipty-v0-2-1-en/) introduced this route, it failed closed on Windows: the engine ships complete ConPTY prebuilds, but its Windows `pause()` / `resume()` are empty methods (zigpty 0.2.1's `WindowsPty`), so consumer-paced output backpressure cannot reach the kernel. The adapter refused readiness rather than run with a queue that grows without bound. The lift condition we wrote down was "upstream adds flow control".

This release stops waiting. UniPty cannot discipline every engine; third-party developers will bring their own backends, and bridging engine differences in adapter code is precisely the point of this architecture. With the gate removed, the route runs on Windows as-is: the adapter keeps draining engine callbacks, and the cost is declared honestly as "output backpressure does not reach the kernel on this platform", the same declared-limitation class the Deno route applies to its internal reader thread. No platform branch is needed anywhere:

```ts
const backend = await createZigptyBackend(); // same line on Windows and unix
```

Support claims stay evidence-gated. Windows tuples remain declared-unverified until public contract evidence exists; the [compatibility catalog](https://unipty.jixoai.com/compatibility) presents them as such. Removing the gate is not a claim of verified support.

## outputSpool: a disk-backed output buffer

A stalled consumer is the main memory risk. A terminal attached to a browser tab that the user switches away from for ten minutes produces ten minutes of output with nowhere to go, piling up in the adapter's queue. Outside Windows the same problem exists; unix kernel backpressure just hands the pressure back to the child, so the pile grows slowly.

`outputSpool` replaces that queue with a disk-backed FIFO:

```ts
const backend = await createZigptyBackend({
  outputSpool: { memoryBytes: 4 * 1024 * 1024 }, // or just `true` for defaults
});
```

The mechanism has three parts. The in-memory head is capped at 1 MiB by default; records beyond it spill to one adapter-owned temp file; replay follows the consumer's pull pace strictly, never enqueuing past the stream's water mark. The public stream is byte-identical with and without the spool: text records round-trip per complete record and chunk boundaries are preserved. When the child exits, the completion signal waits for the backlog to drain, so a fast-exit tail is never cut by EOF; an explicit `close()` still completes synchronously and deletes the temp file.

Three boundaries to know before enabling it. Spill IO is synchronous; disk usage while backlogged is unbounded by design, bounded only by the child's own output; an abruptly-killed process leaves the temp file to OS tmp reaping. On platforms where the engine can pause (unix), passing the memory bound also propagates pressure back into the kernel, blocking the child instead of piling higher.

The path went through a full edge-case battery: 70 package tests covering flood-with-slow-reader ordering, complete replay after an unread exit, mid-backlog cancellation and cleanup, and corrupted-record rejection, plus a 25-scenario contract suite re-run against the packed artifact. Two independent review rounds preceded the release; the three blockers from round one (a transport-release hang on the cancellation path, runtime option validation, and a spec-validation failure) were all fixed before round two passed.

## Other changes

- Fixed a killed flooded child never settling its exit observation while paused reads held a backlog: `terminate()` now resumes master reads after kill ([9bac5d7](https://github.com/jixoai/unipty/commit/9bac5d7))
- Fixed the same hang after `close()`; post-close data now takes the discard path ([9bac5d7](https://github.com/jixoai/unipty/commit/9bac5d7))
- The whole change is recorded as OpenSpec change zigpty-windows-soft-support ([65f053b](https://github.com/jixoai/unipty/commit/65f053b))

See [compare v0.2.1...v0.2.2](https://github.com/jixoai/unipty/compare/v0.2.1...v0.2.2) for the full diff.

## Upgrading

zigpty route users upgrade one package; the other routes need nothing:

```bash
npm i @unipty/backend-zigpty@0.2.1
```

`outputSpool` is off by default; without it, behavior is byte-identical to 0.2.0.
