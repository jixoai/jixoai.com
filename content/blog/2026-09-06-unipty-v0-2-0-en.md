UniPty v0.2.0 is out (the GitHub Release was cut on 2026-08-20). The main content of this release is the **shell-parser ecosystem**: two optional official parser packages that translate command text toward UniPty's structured launch, without ever executing a single byte. With them, all 8 first-phase public packages are on npm together for the first time.

## Background: one contract, three runtimes

Node, Bun, and Deno each expose an incompatible PTY substrate; from installation models and I/O representations to lifecycle semantics and native deployment constraints, everything differs (the opening motivation of the [v1 architecture proposal](https://github.com/jixoai/unipty/blob/main/openspec/changes/archive/2026-08-20-add-unipty-v1-pty-platform/proposal.md)). UniPty's choice is to absorb every one of those differences behind one small, honest contract: Core owns all observable behavior, developers select a Backend explicitly, and support claims are evidence-gated (no claim of support before the full test suite passes).

Earlier on 2026-08-20, the 0.1.x releases landed the core contract and the three official Backend routes (Node over third-party `node-pty`, Bun over runtime-native `Bun.Terminal`, Deno over self-contained `@sigma/pty-ffi`). What v0.2.0 adds is the last capability the v1 architecture had reserved: **optional official Shell Parser packages**. Core accepts only structured argv and never evaluates command text, and consumers migrating from string-command tooling still needed the text → argv translation handled first.

Support claims follow the same honest rules: a runtime/platform tuple is marked `verified` only when the public conformance suite passes in full against the **installed package artifact** (packed and installed into an isolated consumer, driven only through public exports); everything else is honestly `declared-unverified` or `not-targeted`, and failures stay CI diagnostics, never hardening into permanent unsupported claims (see the [conformance docs](https://github.com/jixoai/unipty/blob/v0.2.0/README.md#conformance--compatibility-evidence)).

## Command text ≠ command: @unipty/shell-parser

Consumers migrating from string-command tooling no longer have to hand-write the text → argv translation: `@unipty/shell-parser` classifies command text and translates it into launch-ready structured data, without ever executing a byte. Core has no string-command overload; the implicit shell is precisely the class of accident it exists to eliminate. The package is a synchronous thin wrapper over [unbash](https://www.npmjs.com/package/unbash) whose only public surface is the classification result, with the unbash AST never exposed. The translation target is Core's API contract: `spawn(argv, options)` is synchronous with argv as structured data; `write()` returns boolean readiness, saturation rejecting one whole value with a typed `backpressure` failure; `close()` / `terminate()` are idempotent and synchronous, never cascading; `exited` is repeatably awaitable, independent of stream completion and close ([contract at a glance](https://github.com/jixoai/unipty/blob/v0.2.0/README.md#contract-at-a-glance)).

```ts
import { parse } from "@unipty/shell-parser";

parse("git status --force");
// → { kind: "argv", argv: ["git", "status", "--force"] }

parse("ls *.txt | wc -l");
// → { kind: "script", language: "bash", source: "ls *.txt | wc -l" }

parse("echo 'unterminated");
// → { kind: "incomplete", diagnostics: [...] }
```

The five-way classification `argv | script | incomplete | unsupported | invalid` is the only stable boundary. `argv` means the text was lexically exactly one simple command (quoting and empty arguments preserved) and can go straight to `unipty.spawn(argv)`. `script` means the text carries shell semantics (pipelines and redirection, expansions/substitutions and globs, background or assignment prefixes, ...) and you must explicitly accept the named shell policy before launching anything. Executable resolution (PATH and builtins, functions and aliases) stays your decision; the parser never claims process-launch equivalence for a command name.

The classification policy is deliberately conservative: escaped metacharacters (`echo \*`) and unquoted bracket characters (`[ -f x ]`) also classify as `script`. The walker proves literalness from raw word text, so anything ambiguous stays on the shell-request side, never guessed. See the [package docs](https://github.com/jixoai/unipty/blob/v0.2.0/packages/shell-parser/README.md).

## PowerShell answers to the official parser only: @unipty/powershell-parser

PowerShell command text now translates directly into structured argv too: `@unipty/powershell-parser` answers to exactly one semantic authority, the official `Parser.ParseInput` API, called through an explicitly selected PowerShell host (`pwsh` by default), with no Bash-style guessing. The static adapter script travels as `-EncodedCommand`; your text travels as base64-encoded UTF-8 **on stdin**, never interpolated into a command line, and immune to Windows console code-page ambiguity.

```ts
import { parsePowershell } from "@unipty/powershell-parser";

await parsePowershell('dotnet build -c "My Config"');
// → { kind: "argv", argv: ["dotnet", "build", "-c", "My Config"] }
```

Failures are typed in three parts: missing host → `capability-unavailable` (never a Bash-interpreted result); host starts but exits non-zero or returns an unknown kind → `host-failure` (never a silent downgrade to `script`); exceeded budget (15 s default, configurable via `timeoutMs`) → `host-timeout`.

Host selection is explicit too: `isPowershellHostAvailable()` probes first; `options.host` names another executable (e.g. `powershell` for Windows PowerShell 5.1, which also provides `Parser.ParseInput`). Official `ParseError` records serialize as `{ message, errorId, incomplete, range }` with UTF-16 offsets; errors flagged `IncompleteInput` map to `incomplete`, all others to `invalid`. See the [package docs](https://github.com/jixoai/unipty/blob/v0.2.0/packages/powershell-parser/README.md).

## Release atomicity: parsers first

One release publishes 8 packages, and npm never ends up with a half-published v0.2.0: the [release workflow](https://github.com/jixoai/unipty/blob/v0.2.0/.github/workflows/release.yml) publishes the two parser packages before the core and backends, and the CI comment states the reason. The parsers are the newest names and the most likely to lack a configured Trusted Publisher, so any authentication failure must happen before an already-published core/backend package creates an irreversible partial release. The npm timestamps check out: `@unipty/shell-parser@0.2.0` landed at 11:00:13, `unipty@0.2.0` followed at 11:00:26, and the GitHub Release v0.2.0 was cut at 11:01.

- shell-parser keeps locale strings (`$"..."`) and NUL-bearing ANSI-C words out of argv ([5bcd7d2](https://github.com/jixoai/unipty/commit/5bcd7d2))
- powershell-parser moved text transport to stdin and enforced strict host failures ([7f121ff](https://github.com/jixoai/unipty/commit/7f121ff))
- the docs site consumes the real release-catalog schema and requires the aggregator (aggregation-check) suite's passing stamp ([586e24c](https://github.com/jixoai/unipty/commit/586e24c), [e489776](https://github.com/jixoai/unipty/commit/e489776))

The full list is in [compare v0.1.1...v0.2.0](https://github.com/jixoai/unipty/compare/v0.1.1...v0.2.0).

## Upgrade

No breaking changes. The parser ecosystem is purely additive, with zero changes to Core / Backend / acquisition / helper / conformance code (the [change proposal](https://github.com/jixoai/unipty/blob/main/openspec/changes/archive/2026-08-20-add-shell-parser-ecosystem/proposal.md)'s Impact section, verbatim). Upgrading is:

```bash
npm i unipty@0.2.0
# optional: add the parsers as needed
npm i @unipty/shell-parser@0.2.0 @unipty/powershell-parser@0.2.0
```
