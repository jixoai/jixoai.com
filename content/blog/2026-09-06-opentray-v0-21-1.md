OpenTray v0.21.1 发布了（2026-09-06，仓库的第一份 GitHub Release）。这一版的主菜有双份：**create-opentray 修好了安装失败**，成为 command families 第一个可安装的版本；发布自动化落地，让 jixoai.com 的版本 pill 从「v—」第一次亮成 v0.21.1。

## 背景：轻量工具值得系统级入口

OpenTray 的产品目标从来不是「显示一个托盘图标」——[AGENTS.md 的 Vision](https://github.com/jixoai/opentray/blob/main/AGENTS.md) 一句话讲完：给轻量工具一个系统级入口，**不必强迫用户背上 Electron 或整套桌面应用框架**。CLI 工具、AI skill、本地守护进程，它们值得常驻状态面与点击入口，但为一个小图标引入上百 MB 的运行时不成立。

当前的答案是托盘优先的平台模型，四个本体各就各位：

- `App`：调用方持有的运行时身份与隔离边界
- `Tray`：归属该 app 的单个桌面状态原子
- `Session`：托盘事件与变更的实时权威来源
- `Extension`：作用域限定在 app 与托盘上的原生能力原子

应用代码直接 `createTray()`，自行持有前台/后台生命周期（`Space`/`Surface` 时代的旧本体已从公共 API 退役）。第一个应用不需要打包器，也不加载 Node addon——普通应用代码经公共 tray/session 协议与运行时对话：

```ts
import { createTray, type TrayIcon } from "opentray";

let tray;
tray = await createTray(
  {
    id: "com.example.first-app",
    icon: { "text-only": "OT" },
    menu: {
      items: [
        { title: "Quit", primaryEvent: true, onMenuClick: () => void tray.destroy() },
      ],
    },
  },
  { appId: "com.example.first-app", appName: "First App" },
);
```

工作区是一整个固定版本家族：`opentray`（SDK + CLI）、`@opentray/spec`（协议契约）、`@opentray/packaging` 与四个 bundler 适配器（vite/tsdown/esbuild/webpack 同一 manifest 形状）、`@opentray/ext-webview` 及平台 WebView 动态库、`@opentray/ext-badge`，Lynx 扩展独立维护在 [jixoai/opentray-ext-lynx](https://github.com/jixoai/opentray-ext-lynx)。

## 一行命令，把现有命令变成托盘应用

已经有在本地服务 HTTP 的命令？`npx create-opentray` 把它包装成 OpenTray 托管的应用，三条进入路径（[create-app 指南](https://github.com/jixoai/opentray/blob/main/skills/opentray/references/create-app.md)）：

```bash
npx create-opentray web      # 浏览器向导，交互式
npx create-opentray create --app-id com.example.build \
  --app-name "Build" --exec "npm run dev"   # 完全非交互
npx create-opentray skill    # 内置 AI skill，交给代理读
```

0.21.0 的 command families 把向导的命令输入收敛成单行输入组：家族选择前缀 + 命令体。npm（npx/pnpx/bunx/yarn dlx/nubx/deno run/vpx）、`go run`、`cargo install`、`uvx/pipx run`、`dnx` 每个家族渲染成只读命令面，点开结构化表单（runner、包名/模块/crate/工具 id、版本、参数）；确认写回命令串，取消整场作废。家族感知的 appId 推导是同一个包跨 runner 的稳定身份：

```text
npx @deepseek-ai/dsh@latest web   → web.dsh.npmjs
go run rsc.io/fortune@latest      → fortune.golang
cargo install ripgrep（rg）        → rg.rust
```

## 修复安装 404：0.21.1 是第一个可安装的版本

诚实地说：**0.21.0 对全新安装是坏的**（[0b0fe63](https://github.com/jixoai/opentray/commit/0b0fe632)）。`@create-opentray/core` 与 `@create-opentray/cli` 是私有 workspace 构建原子，npm 上不存在，却被放进了运行时 `dependencies`——tsdown 只把 devDependencies 里的 workspace 包打进产物，`dependencies` 里的包保持 external、留给消费者从 registry 解析。于是消费者 `npm i create-opentray` 直接 404。

修复是语义归位，不是绕路：

```diff
- "dependencies":   { "@create-opentray/core": "workspace:*",
-                     "@create-opentray/cli":  "workspace:*" }
+ "devDependencies": { "@create-opentray/core": "workspace:*",
+                      "@create-opentray/cli":  "workspace:*" }
```

私有的构建原子进 devDependencies，tsdown 将它们 bundle 进单包产物——发布物里零残留 import，依赖清单里只剩 registry 上真实存在的包名。`@opentray/spec`、`@opentray/packaging`、`@opentray/vite-plugin` 同船 0.21.1。

## 发布自动化：GitHub Releases 成为 L1

此前这个仓库经 changesets 发 npm 包，但**零 GitHub Releases**——本站的版本 pill 长期显示「v—」，org blog 也没有 L1 可链。[变更提案](https://github.com/jixoai/opentray/blob/main/openspec/changes/archive/2026-09-06-release-automation-and-copy/proposal.md)补上了管道：每个发布版本同时切出 GitHub Release（tag = 包版本，notes = changesets 生成的 changelog 节）；workflow_dispatch 允许为当前版本补切 bootstrap release。opentray@0.21.1 就是走 bootstrap 路径切出的第一份——从下一个版本起，release notes 全自动。

## 升级

```bash
npm i create-opentray@0.21.1   # 0.21.0 用户必升（旧版装不上）
npm i opentray@0.21.1          # SDK 同线
```

使用官方扩展时锁同一条协议线：`pnpm add opentray@stable-A-B @opentray/ext-webview@stable-A-B`（协议线 tag 由 `@opentray/spec` 发布，勿与 `latest` 混用）。

## 致谢

那条 devDependencies 修复的判定规则，来自一次真实的安装失败反馈（2026-08-20 的用户纠偏实证）——404 是最好的测试用例。
