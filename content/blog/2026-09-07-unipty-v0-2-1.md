UniPty v0.2.1 发布了（GitHub Release 于 2026-09-07 12:21 UTC 切出）。这一版的主菜是第四条官方 Backend 路由 `@unipty/backend-zigpty`：Node 侧第一次可以在 `node-pty` 之外换一个 PTY 引擎，业务代码一行不改。

## 为什么 Node 可以有第二条路由

UniPty 的路由注册表按底座身份索引，不按运行时。一条路由是一个具体引擎加上它如实声明的能力面，运行时只是声明里的一格。这条法则在 v0.2.1 之前是理论，现在有了第一个实例：同一个 Node 运行时下，`node-pty` 与 `zigpty` 各自是一条独立路由，各自出各自的验证证据，发布门禁也各自把关。这次发布把门禁本身也升级了，catalog 聚合对每条路由校验「包名 + backend id」二元组，两条 Node 路由没法互换身份替对方凑数（[f083127](https://github.com/jixoai/unipty/commit/f083127)）。

## zigpty 是个什么样的引擎

[zigpty](https://github.com/pithings/zigpty)（npm `zigpty@0.2.1`，MIT，[pi0](https://github.com/pi0) 维护）用 Zig 实现了跨平台 PTY，再以 NAPI 绑定暴露给 Node。对使用者来说，它最实在的特点落在分发模型上。

| 维度 | zigpty 的答案 |
| --- | --- |
| 运行时依赖 | 0 个 |
| 预编译覆盖 | 8 个平台元组（linux/macos/windows × x64/arm64，glibc 与 musl） |
| 分发方式 | 全部预编译打进 npm tarball，解包约 420KB |
| 安装脚本 | 没有 postinstall，不碰 node-gyp |

对比一下就知道这意味着什么。`@lydell/node-pty` 走平台子包（optionalDependencies 按平台各装一份），Bun 与 Deno 依赖运行时内置或内嵌动态库。zigpty 是「装完即得」，`--omit=optional` 之类 的安装姿势都不会把它弄坏。

它还有一处我们欣赏的设计。预编译加载失败时，上游库会静默回退到基于管道的伪 PTY；UniPty 的适配器在就绪阶段硬门禁这个回退，`hasNative` 不真就直接给 `unsupported`，绝不拿着假 PTY 冒充真的（isatty 与内核几何尺寸在伪 PTY 上都不成立）。

## 怎么用

安装然后换一行工厂调用，其余代码与另外三条路由完全一致：

```bash
npm install unipty @unipty/backend-zigpty
```

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

`spawn` 仍是结构化 argv，`write()` 仍返回布尔就绪，`close()` 与 `terminate()` 依旧不级联，`exited` 依旧独立可重复 await。25 个场景的公共契约套件对安装后的包产物全量跑过：darwin-arm64 本地一份原生证据，CI 的 ubuntu 与 macos 各一份，进了[发布目录](https://unipty.jixoai.com/compatibility)。

## 四个注意事项

这四条都写进了 [README 的能力差异矩阵](https://github.com/jixoai/unipty/blob/v0.2.1/README.md#capability-differences-what-the-engines-actually-give-you)。下面挑使用前必须知道的四条。

**1. 写入是文本原生的。** zigpty 的 `write` 只收字符串，所以 Endpoint 默认拒绝字节输入并给 `unsupported`。你的输入流如果是字节（xterm.js 前端、协议转发这类场景），开一个选项即可：

```ts
const backend = await createZigptyBackend({ writeDecode: true });

// 现在字节输入合法：经有状态流式解码，跨 chunk 的多字节序列是安全的
pty.write(new TextEncoder().encode("echo héllo\r"));
```

`writeDecode` 是 Backend 自有的便捷项，fatal 解码策略会整值拒绝而不是替换成乱码。

**2. Windows 上失败关闭。** zigpty 带了 ConPTY 预编译，但它的 `pause()` / `resume()` 在 win32 上是空操作，输出背压没法传导到内核。适配器因此在 Windows 上拒绝就绪，元数据 targets 收窄到 darwin 与 linux。有真实的 Windows 契约证据之前，这个门禁不解除。

**3. 传输 EOF 是接出来的。** 这个引擎不暴露传输层事件，适配器在退出窗口接管主读流，拿真实的 `end` / `close` 当 EOF，另有一个 50ms 的静默窗兜底（迟到的数据会续期这个窗口，不会被截断）。代价是传输读错误与干净 EOF 在这条路由上不可区分，这是如实声明的限制，不是没写文档。

**4. 退出观察有它自己的形状。** 信号致死时报 `{ exitCode: 0, signal: "SIGTERM" }`，退出码保持引擎报告的原值而不是伪造一个 null；可执行文件缺失则是 `{ exitCode: 1, signal: null }` 的退出观察，不是 spawn 异常。

<summary>示例：四条路由的信号致死报告形状对照</summary>

```text
node-pty   { exitCode: null, signal: "SIGTERM" }
zigpty     { exitCode: 0,    signal: "SIGTERM" }

```

## 其余变更

- 修复 ubuntu 上快退子进程输出丢失：zigpty 的退出回调会同步销毁读流且无 flush，适配器改为在退出窗口接管读流（[3d56f71](https://github.com/jixoai/unipty/commit/3d56f71)）
- 修复 writeDecode 饱和拒绝推进解码器状态的问题：字节值改为原始准入、泵送时解码，被拒绝的值重试结果逐字一致（[f083127](https://github.com/jixoai/unipty/commit/f083127)）
- 发布目录注册表重构为按路由身份键控并做双重身份校验（[b878ce4](https://github.com/jixoai/unipty/commit/b878ce4)、[f083127](https://github.com/jixoai/unipty/commit/f083127)）
- 文档全仓同步第四条路由：README 双语、架构设计、贡献规范、文档站（[021a82d](https://github.com/jixoai/unipty/commit/021a82d)）

完整清单见 [compare v0.2.0...v0.2.1](https://github.com/jixoai/unipty/compare/v0.2.0...v0.2.1)。

## 升级

无破坏性变更。zigpty 路由是纯新增包，Core 与既有三条路由零改动：

```bash
npm i @unipty/backend-zigpty@0.2.0
```

已经在用 `unipty@0.2.0` 的话，Core 不用动。
