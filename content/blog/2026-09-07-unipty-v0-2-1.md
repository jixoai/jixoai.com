UniPty v0.2.1 发布了（GitHub Release 于 2026-09-07 12:21 UTC 切出）。这一版让 Node 侧第一次能换 PTY 引擎：新的官方 Backend 包 `@unipty/backend-zigpty` 接入 Zig 实现的引擎 zigpty，装一个包、换一行创建 Backend 的代码，业务代码原样运行。`@unipty/backend-zigpty@0.2.0` 于 12:21 UTC 上架 npm，GitHub Release 同分钟切出。

## 背景：为什么 Node 现在能换引擎

UniPty 的 Node 路由一直跑在 node-pty 上（经 `@lydell/node-pty` 预构建分发）。它的预编译拆在平台子包里，optionalDependencies 按平台各装一份，装出来的结果依赖安装器对 optional 依赖的处理；哪台机器装出什么，取决于安装姿势而不是你的代码。出了问题没有第二个选项。你只能回头修安装环境。

UniPty 在 2026-08 的 v1 架构提案里就把引擎设计成显式替换件：Core 拥有全部可观察行为，你把选中的 Backend 注入 `new UniPty({ backend })`，注册表按引擎身份索引而不按运行时，同一个运行时可以挂多个引擎。设计一直允许，实际可装的只有一个。v0.2.1 补上 zigpty，这也是「同一运行时挂多条引擎」的第一个实例。发布目录（compatibility 页面背后的证据表）的聚合校验同步升级，对每条路由同时核对包名与引擎身份（[f083127](https://github.com/jixoai/unipty/commit/f083127)），两个 Node 引擎没法互换身份替对方凑数。

## zigpty：一个装完即得的引擎

[zigpty](https://github.com/pithings/zigpty)（npm `zigpty@0.2.1`，MIT，[pi0](https://github.com/pi0) 维护）用 Zig 实现跨平台 PTY，经 NAPI 绑定暴露给 Node。对使用者，它最实在的特点是分发模型：

| 维度 | zigpty 的答案 |
| --- | --- |
| 运行时依赖 | 0 个 |
| 预编译覆盖 | 8 个平台元组（linux/macos/windows × x64/arm64，glibc 与 musl） |
| 分发方式 | 全部预编译打进 npm tarball，解包约 420KB |
| 安装脚本 | 没有 postinstall，不碰 node-gyp |

对照着看更清楚：`@lydell/node-pty` 把预编译放进平台子包，optionalDependencies 按平台各装一份；Bun 与 Deno 的路由依赖运行时内置或内嵌的动态库；zigpty 的 8 个平台元组全部打进主包，装完即得，`--omit=optional` 之类的安装姿势不会把它弄坏。安装就这一行：

```bash
npm install unipty @unipty/backend-zigpty
```

上游有一处要当心的行为：预编译加载失败时，zigpty 库会静默回退到基于管道的伪 PTY，而 isatty 与内核几何尺寸在伪 PTY 上都不成立。UniPty 的适配器在就绪阶段硬门禁这个回退，`hasNative` 不真就直接给 `unsupported`，绝不拿假 PTY 冒充真的。

## 换引擎，改一行就够

已经在用 unipty 的项目，接入 zigpty 只动创建 Backend 的那一行：

```ts
import { UniPty } from "unipty";
import { createZigptyBackend } from "@unipty/backend-zigpty";

const backend = await createZigptyBackend();
const unipty = new UniPty({ backend });

const pty = unipty.spawn(["/bin/sh", "-i"], {
  terminal: { cols: 120, rows: 40 },
});
for await (const text of pty.stream({ encoding: "utf8" })) {
  process.stdout.write(text);
}
```

工厂调用之后全是熟悉的那套契约。`spawn` 收结构化 argv，`write()` 返回布尔就绪，`close()` 与 `terminate()` 幂等且不级联，`exited` 独立可重复 await。换引擎不换语义。25 个场景的公共契约套件对安装后的包产物全量跑过，darwin-arm64 本地一份原生证据，CI 的 ubuntu 与 macos 各一份，全部进了[发布目录](https://unipty.jixoai.com/compatibility)。

## 接入时踩过的两个坑

新引擎不会一次接顺。这条路由在发布前修掉了两个真实的坑，今天装到的包里没有它们。

第一个坑在 ubuntu 上：子进程退出极快时，输出会丢。zigpty 的退出回调会同步销毁读流且没有 flush，缓冲里的数据来不及送出。适配器改为在退出窗口接管读流，最后一段输出现在完整交到你手上（[3d56f71](https://github.com/jixoai/unipty/commit/3d56f71)）。

第二个坑藏在 `writeDecode` 里：写入因背压被拒绝时，解码器状态却已经前移，重试同一份数据可能得到不同结果。修复把准入与解码拆开，字节值原始进入队列、真正泵送时才解码，被拒绝的值重试结果逐字一致（[f083127](https://github.com/jixoai/unipty/commit/f083127)）。

这两个问题都不长在公共 API 的形状上，只有真实跑契约套件才能暴露。这也是 UniPty 坚持全量契约证据的原因。

## 用之前要知道的四件事

引擎之间有真实差异。下面四条都写进了 [README 的能力差异矩阵](https://github.com/jixoai/unipty/blob/v0.2.1/README.md#capability-differences-what-the-engines-actually-give-you)，换引擎之前值得过一遍。

**1. 写入是文本原生的。** zigpty 的 `write` 只收字符串，Endpoint 默认拒绝字节输入并给 `unsupported`。你的输入流如果是字节（xterm.js 前端、协议转发这类场景），开一个选项即可：

```ts
const backend = await createZigptyBackend({ writeDecode: true });

// 现在字节输入合法：经有状态流式解码，跨 chunk 的多字节序列是安全的
pty.write(new TextEncoder().encode("echo héllo\r"));
```

`writeDecode` 是 Backend 自有的便捷项，fatal 解码策略会整值拒绝而不是替换成乱码；它的解码路径就是上面修过原子性的那条。

**2. Windows 上失败关闭。** zigpty 带了 ConPTY 预编译，但它的 `pause()` / `resume()` 在 win32 上是空操作，输出背压没法传导到内核。适配器因此在 Windows 上拒绝就绪，元数据 targets 收窄到 darwin 与 linux。有真实的 Windows 契约证据之前，这个门禁不解除。

**3. 传输 EOF 是接出来的。** 这个引擎不暴露传输层事件，适配器在退出窗口接管主读流，拿真实的 `end` / `close` 当 EOF，另有一个 50ms 的静默窗兜底（迟到的数据会续期这个窗口，不会被截断）。代价是传输读错误与干净 EOF 在这条路由上不可区分，这是如实声明的限制。接管读流正是上面第一个坑的修法。

**4. 退出观察有它自己的形状。** 信号致死时报 `{ exitCode: 0, signal: "SIGTERM" }`，退出码保持引擎报告的原值而不是伪造一个 null；可执行文件缺失则是 `{ exitCode: 1, signal: null }` 的退出观察，不是 spawn 异常。

```text
zigpty     { exitCode: 0,    signal: "SIGTERM" }

```

## 其余变更

- 修复 ubuntu 上快退子进程输出丢失：zigpty 的退出回调会同步销毁读流且无 flush，适配器改为在退出窗口接管读流（[3d56f71](https://github.com/jixoai/unipty/commit/3d56f71)）
- 修复 writeDecode 饱和拒绝推进解码器状态的问题：字节值改为原始准入、泵送时解码，被拒绝的值重试结果逐字一致（[f083127](https://github.com/jixoai/unipty/commit/f083127)）
- 发布目录注册表重构为按路由身份键控并做双重身份校验（[b878ce4](https://github.com/jixoai/unipty/commit/b878ce4)、[f083127](https://github.com/jixoai/unipty/commit/f083127)）

## 升级

无破坏性变更。zigpty 路由是纯新增包，Core 与既有三条路由零改动。Backend 包在 npm 上的版本是 0.2.0，安装时以这个号为准：

```bash
npm i @unipty/backend-zigpty@0.2.0
```

已经在用 `unipty@0.2.0` 的话，Core 不用动。
