OpenTray v0.21.1 is out (2026-09-06, the repo's first GitHub Release). The headline is double: **create-opentray's install failure is fixed**, making this the first installable release of command families; and release automation has landed, turning this site's version pill from "v—" to v0.21.1 for the first time.

## Background: lightweight tools deserve a system-level entry

OpenTray's product goal was never "show a tray icon" — the [AGENTS.md Vision](https://github.com/jixoai/opentray/blob/main/AGENTS.md) says it in one line: give lightweight tools a system-level entry point **without forcing users into Electron or a full desktop app framework**. CLI tools, AI skills, local daemons deserve a resident status surface and a click entry — but a hundred-MB runtime for one small icon is not a deal.

The current answer is the tray-first platform model, four atoms each in place:

- `App`: the caller-owned runtime identity and isolation boundary
- `Tray`: one desktop status atom owned by that app/runtime
- `Session`: the live source of authority for tray events and mutations
- `Extension`: an optional native capability atom scoped to app and tray

Application code calls `createTray()` directly and owns its own foreground/background lifetime (the `Space`/`Surface`-era ontology has retired from the public API). The first app needs no bundler and loads no Node addon — ordinary app code talks to the runtime over the public tray/session protocol:

```ts
import { createTray, type TrayIcon } from "opentray";

let tray;
tray = await createTray(
  {
    id: "com.example.first-app",
    icon: { "text-only": "OT" },
    menu: {
      items: [
        { title: "Quit", primaryEvent: true, onMenuClick: () => void tray.destroy() },
      ],
    },
  },
  { appId: "com.example.first-app", appName: "First App" },
);
```

The workspace is one fixed-version family: `opentray` (SDK + CLI), `@opentray/spec` (the protocol contract), `@opentray/packaging` with four bundler adapters (vite/tsdown/esbuild/webpack writing the same manifest shape), `@opentray/ext-webview` with platform WebView dynamic libraries, `@opentray/ext-badge`; the Lynx extension lives in its own repo, [jixoai/opentray-ext-lynx](https://github.com/jixoai/opentray-ext-lynx).

## One command turns an existing command into a tray app

Already have a command that serves HTTP locally? `npx create-opentray` wraps it into an OpenTray-hosted app, with three entry paths (the [create-app guide](https://github.com/jixoai/opentray/blob/main/skills/opentray/references/create-app.md)):

```bash
npx create-opentray web      # browser wizard, interactive
npx create-opentray create --app-id com.example.build \
  --app-name "Build" --exec "npm run dev"   # fully non-interactive
npx create-opentray skill    # the built-in AI skill, for agents to read
```

The 0.21.0 command families collapsed the wizard's command input into a single-row input group: a family-selector prefix plus the command body. npm (npx/pnpx/bunx/yarn dlx/nubx/deno run/vpx), `go run`, `cargo install`, `uvx/pipx run`, and `dnx` each render a read-only command surface opening a structured form (runner, package/module/crate/tool id, version, arguments); confirm writes the command string back, cancel discards the whole dialog session. The family-aware appId derivation is a stable identity for the same package across runners:

```text
npx @deepseek-ai/dsh@latest web   → web.dsh.npmjs
go run rsc.io/fortune@latest      → fortune.golang
cargo install ripgrep (rg)        → rg.rust
```

## The install-404 fix: 0.21.1 is the first installable release

Honestly: **0.21.0 is broken for fresh installs** ([0b0fe63](https://github.com/jixoai/opentray/commit/0b0fe632)). `@create-opentray/core` and `@create-opentray/cli` are private workspace build atoms that do not exist on npm, yet they shipped as runtime `dependencies` — tsdown only bundles workspace packages from devDependencies; packages in `dependencies` stay external, left for the consumer to resolve from the registry. Consumers running `npm i create-opentray` hit a 404.

The fix is semantics put back in place, not a detour:

```diff
- "dependencies":   { "@create-opentray/core": "workspace:*",
-                     "@create-opentray/cli":  "workspace:*" }
+ "devDependencies": { "@create-opentray/core": "workspace:*",
+                      "@create-opentray/cli":  "workspace:*" }
```

Private build atoms move to devDependencies, and tsdown bundles them into the single-package dist — zero residual imports in the artifact, only registry-real package names left in the dependency manifest. `@opentray/spec`, `@opentray/packaging`, and `@opentray/vite-plugin` ride along at 0.21.1.

## Release automation: GitHub Releases become the L1

Until now this repo published npm packages via changesets with **zero GitHub Releases** — this site's pill read "v—" and the org blog had no L1 to link. The [change proposal](https://github.com/jixoai/opentray/blob/main/openspec/changes/archive/2026-09-06-release-automation-and-copy/proposal.md) closed that: every published version also cuts a GitHub Release (tag = the package version, notes = the changesets-generated changelog section); a `workflow_dispatch` input can cut a release for the current version without a bump (the bootstrap path). opentray@0.21.1 is the first one, cut via that bootstrap path — from the next version on, release notes are fully automated.

## Upgrade

```bash
npm i create-opentray@0.21.1   # mandatory for 0.21.0 users (it never installed)
npm i opentray@0.21.1          # the SDK, same line
```

When using official extensions, lock the same protocol line: `pnpm add opentray@stable-A-B @opentray/ext-webview@stable-A-B` (protocol-line tags are published by `@opentray/spec`; do not mix with `latest`).

## Acknowledgements

The devDependencies rule behind that fix came from a real install-failure report (the 2026-08-20 user-correction case) — a 404 is the best test case.
